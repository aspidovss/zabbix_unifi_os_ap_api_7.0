# Zabbix_unifi_os_ap_api_7.0

**UniFi Network API — шаблон Zabbix 7.0 для точек доступа UniFi OS**

[English](README.md) | **Русский**

Шаблон Zabbix 7.0 для мониторинга **UniFi Network**. Он сам находит все сайты и все точки доступа контроллера и ставит их на мониторинг. Подключение к контроллеру идёт по **API-ключу**, ключ можно хранить в **HashiCorp Vault**.

- **Версия:** 1.0.0
- **Zabbix:** 7.0
- **Лицензия:** MIT
- **Автор:** AspidovSS

Это форк проекта [MassimilianoPasquini97/zbx_unifi_network_api](https://github.com/MassimilianoPasquini97/zbx_unifi_network_api) (Zabbix 7.4), переработанный под Zabbix 7.0 и расширенный. Подробнее — в разделе [Благодарности](#благодарности).

## Возможности

- **Автоматическое обнаружение.** Отдельный хост Zabbix на каждый сайт и на каждую точку доступа, по всем сайтам контроллера. Коммутаторы и шлюзы не попадают: точкой доступа считается устройство, которое UniFi помечает признаком `accessPoint`.
- **Состояние точки.** Статус, CPU, память, load average, uptime, прошивка.
- **Метрики каждого радиомодуля** (2.4 / 5 / 6 ГГц):
  - канал, ширина, мощность, EIRP, усиление антенны;
  - утилизация канала (Busy / Rx / Tx);
  - Tx Retry, Tx/Rx Dropped;
  - пакеты и байты в секунду;
  - клиенты, Wi-Fi Experience.
- **Uplink.**
  - Вышестоящее устройство (имя UniFi, имя LLDP или MAC), порт, тип.
  - Скорость, с тревогой при её падении.
  - Трафик Down/Up.
- **Клиенты.**
  - Клиенты на точке и на каждом радио, гости, среднее время подключения и список подключённых устройств.
  - Число Wi-Fi-клиентов на сайте.
- **Аномалии UniFi.**
  - Аномалии самой точки: потеря кадров, медленное подключение клиентов.
  - Какие клиенты точки сейчас с аномалиями. Это показывает, в чём проблема: в клиенте или в зоне Wi-Fi.
- **Пороги для промышленных объектов.** Отдельные пороги для 2.4 и 5 ГГц (контекстные макросы). Тревоги Tx Retry не срабатывают при малом трафике.
- **Безопасное обнаружение.** Если API не ответил хотя бы по одному сайту, discovery пропускает этот проход. Точки доступа этого сайта не считаются потерянными и не удаляются.
- **Секреты в Vault.** API-ключ хранится как макрос-секрет Vault. Сырые ответы API не сохраняются, а ключи устройств из ответа внутреннего API вырезаются при предобработке.

## Как это работает

```
Хост «UniFi Network API»  (создаёте вы, шаблон «UniFi Network API»)
 │
 ├─ Discovery Sites  (раз в сутки)
 │    └─ UniFi [<сайт>] - Site                 шаблон «UniFi Network API - Site»
 │         Wi-Fi-клиенты, точки всего / онлайн / офлайн
 │
 └─ Discovery Access Points  (список раз в 30 мин, discovery при изменении или раз в сутки)
      └─ UniFi [<сайт>] - AP:<имя>             шаблон «UniFi Network API - Access Point»
           состояние, CPU, память, радио, uplink, клиенты, аномалии
```

Zabbix 7.0 не запускает хост-прототипы на обнаруженных хостах, это появилось только в 7.4. Поэтому точки доступа находит основной хост, а не хосты сайтов.

Шаблон использует два API UniFi, оба с одним и тем же API-ключом (заголовок `X-API-KEY`):

| API | Путь | Для чего |
|---|---|---|
| Официальный Integration API v1 | `/proxy/network/integration/v1/...` | сайты, устройства, клиенты, статистика устройств |
| Внутренний Network API | `/proxy/network/api/s/<сайт>/stat/device/<mac>`, `/stat/anomalies` | радио, uplink, аномалии |

Внутренний API официально не документирован и может измениться в будущих версиях UniFi (см. [Ограничения](#ограничения)).

## Требования

- **Zabbix 7.0**, сервер или прокси. Шаблон использует элементы HTTP agent, Script и Dependent.
- **UniFi Network** с Integration API (UniFi Network 9.x и новее). Контроллер должен работать на **UniFi OS**: UDM / UCG / UDR / Cloud Key Gen2+ / UniFi OS Server. Шаблон использует префикс пути `/proxy/network`.
- **Сетевой доступ.** Zabbix-сервер или прокси должен достучаться до консоли по HTTPS. Порт может быть нестандартным, например `192.168.1.10:11443`.
- **API-ключ UniFi.**
- **(Рекомендуется) HashiCorp Vault**, подключённый к Zabbix (KV v2). Без Vault ключ хранится в макросе типа *Секретный текст*.

## Установка

### 1. Создайте API-ключ в UniFi

UniFi Network → **Settings → Control Plane → Integrations → Create API Key**. Скопируйте ключ: он показывается один раз.

Проверьте ключ с Zabbix-сервера. Не вводите ключ прямо в команду:

```bash
read -s KEY        # вставьте ключ, он не отображается
curl -sk -H "X-API-KEY: $KEY" "https://<консоль>/proxy/network/integration/v1/sites"
```

В ответ должен прийти JSON со списком сайтов в `data`.

### 2. Положите ключ в Vault

```bash
vault kv put secret/zabbix/unifi api-key="<ключ>"
```

В Zabbix значение макроса Vault записывается как `путь:ключ`. Для движка KV v2, смонтированного как `secret`, это `secret/zabbix/unifi:api-key`. Если точка монтирования другая, первая часть пути — это точка монтирования.

### 3. Создайте глобальные макросы

**Администрирование → Макросы:**

| Макрос | Тип | Пример |
|---|---|---|
| `{$UNIFI_NETWORK_API_ADDRESS}` | Текст | `192.168.1.10` или `unifi.example.local:11443`. Без `https://` и пробелов. |
| `{$UNIFI_NETWORK_API_KEY}` | Секрет Vault | `secret/zabbix/unifi:api-key` |

Оба макроса **обязательно глобальные**. Хосты сайтов и точек доступа создаются через discovery и не наследуют макросы основного хоста. На шаблонах эти макросы тоже не задавайте: макрос шаблона перекрывает глобальный.

### 4. (Необязательно) Создайте родительскую группу

Найденные хосты попадают в группы `UniFi Network/Sites` и `UniFi Network/Access Points`. Zabbix показывает их как подгруппы, только если существует группа с именем ровно **`UniFi Network`**.

### 5. Импортируйте шаблон

**Сбор данных → Шаблоны → Импорт** → `template/zbx_unifi_network_api_7.0.yaml`.

### 6. Создайте основной хост

Создайте хост с любым именем, например `UniFi Controller`. Интерфейс ему не нужен. Привяжите шаблон **UniFi Network API**.

### 7. Запустите обнаружение

По умолчанию discovery запускается раз в сутки. Чтобы запустить сейчас, откройте основной хост и нажмите **Execute now** у элементов:

1. **Sites JSON**, затем **Discovery Sites**;
2. **Access Points JSON (all sites)**, затем **Discovery Access Points**.

Через 1–2 минуты хосты появятся в `UniFi Network/Sites` и `UniFi Network/Access Points`. Радио-элементы появятся после первого опроса каждой точки, примерно через 2 минуты.

## Обновление

Импортируйте новую версию файла с такими правилами импорта:

- **«Обновить существующие»** для групп, шаблонов, элементов, триггеров и правил обнаружения;
- **«Удалить отсутствующие»** для элементов, триггеров, правил обнаружения и прототипов.

Изменения имён и групп дойдут до существующих хостов при следующем проходе discovery. Чтобы применить их сразу, нажмите **Execute now**, как в шаге 7.

## Хосты, группы и теги

| Хост | Имя | Группа |
|---|---|---|
| Сайт | `UniFi [<сайт>] - Site` | `UniFi Network/Sites` |
| Точка доступа | `UniFi [<сайт>] - AP:<имя точки>` | `UniFi Network/Access Points` |

**Теги хостов:**

- `UniFi Type` = `Site` / `Access Point`
- `UniFi Site` = имя сайта
- `UniFi Model` = модель точки

**Теги элементов:**

- `UniFi Component` = `System`, `CPU`, `Memory`, `Clients`, `Radio`, `Uplink`, `Anomalies`, `Access Points`, `Raw`
- `UniFi Radio` = `2.4GHz` / `5GHz` / `6GHz`

Все теги начинаются с `UniFi` и всегда имеют значение.

## Что мониторится

### Основной хост (`UniFi Network API`)

- Версия приложения UniFi Network.
- Число точек доступа и точек офлайн по всем сайтам.

### Сайт (`UniFi Network API - Site`)

- Wi-Fi-клиенты на сайте. Собираются все клиенты, постранично по 200 за запрос.
- Точки доступа: всего, онлайн, офлайн.

### Точка доступа (`UniFi Network API - Access Point`)

| Группа | Элементы |
|---|---|
| Система | состояние, модель, имя, IP, MAC, прошивка, uptime, load average |
| CPU / память | загрузка, % |
| Клиенты | всего, гости, среднее время подключения, список клиентов (`имя \| IP \| MAC`), Wi-Fi Experience |
| Uplink | вышестоящее устройство, его MAC / порт / описание LLDP, тип (кабель / mesh), скорость, скорость Down/Up, пакеты, счётчики байт |
| Радио (каждый диапазон) | состояние, канал, ширина, мощность, EIRP, усиление антенны, клиенты, гости, Wi-Fi Experience, утилизация канала Busy/Rx/Tx, Tx Retry %, Tx/Rx пакеты/с и байты/с, Tx/Rx Dropped % |
| Аномалии | активные аномалии точки, длительность потери кадров, медленные подключения за час, клиенты с аномалиями (число, %, список) |

**Частота записи для редко меняющихся значений:**

- EIRP, усиление антенны, тип uplink: записываются при изменении и не реже раза в сутки.
- Ширина канала, скорость uplink: записываются при изменении и не реже раза в час.

Эти значения всё равно приходят из обычного запроса раз в 2 минуты. Отдельных запросов ради них не делается.

## Триггеры

### Основной хост

| Триггер | Уровень | Условие по умолчанию |
|---|---|---|
| Application Version Changed | Info | версия изменилась |
| No Data for 30m | High | API не отвечает дольше `{$TRIGGER_NODATA}` |

### Точка доступа

| Триггер | Уровень | Условие по умолчанию |
|---|---|---|
| State is "OFFLINE / CONNECTION_INTERRUPTED / ISOLATED" | High | текущее состояние |
| State is "PENDING_ADOPTION / DELETING" | Warning | текущее состояние |
| State is "UPDATING / GETTING_READY" | Info | текущее состояние |
| CPU at … | Warning / Average | среднее за 3 значения > 80% / 90% |
| Memory at … | Warning / Average | среднее за 3 значения > 80% / 90% |
| Device Rebooted | Info | uptime уменьшился |
| Too many clients on AP | Warning | > 40 клиентов в течение 15 мин |
| Uplink parent device changed | Info | точку подключили к другому устройству |
| Uplink speed dropped | Warning | скорость проводного uplink ниже своего максимума за 7 дней, например 1 Гбит/с → 100 Мбит/с |
| Radio … state is "…" for 10m | Average | радио не было в `RUN` все 10 минут |
| Radio … channel utilization | Warning / Average | 5 ГГц: > 50% / 70%; 2.4 ГГц: > 60% / 80%; 15 мин |
| Radio … Tx Retry | Warning / Average | 5 ГГц: среднее > 15% / минимум > 25%; 2.4 ГГц: среднее > 25% / минимум > 40%; за 1 ч, только если радио передаёт > 20 пакетов/с |
| AP high drop rate (UniFi anomaly) | Warning | аномалия длится ≥ 15 мин |
| Clients connect slowly to AP (UniFi anomaly) | Warning | ≥ 3 пятиминутных интервала за час |
| Wi-Fi zone problem | Warning | ≥ 30% и ≥ 3 клиентов точки с аномалиями в течение 15 мин |

Пороги подобраны для **промышленных объектов**, где много металла и движущейся техники. Для офисов их стоит понизить в макросах. Если разным объектам нужны разные значения, переопределите их на уровне хоста или шаблона.

| `{$TRIGGER_RADIO_STATE_TIME}` | `10m` | Тревога, если радио не в RUN весь этот период |
| `{$TRIGGER_TXRETRIES_AVERAGE:"2.4GHz"}` | `40` | Tx Retry, Average, %, 2.4 ГГц |
| `{$TRIGGER_TXRETRIES_AVERAGE}` | `25` | Tx Retry, Average, %, по умолчанию (5/6 ГГц) |
| `{$TRIGGER_TXRETRIES_MIN_PPS}` | `20` | Триггеры Tx Retry работают, только если радио передаёт больше N пакетов/с |
| `{$TRIGGER_TXRETRIES_TIME}` | `1h` | Период оценки Tx Retry |
| `{$TRIGGER_TXRETRIES_WARNING:"2.4GHz"}` | `25` | Tx Retry, Warning, %, 2.4 ГГц |
| `{$TRIGGER_TXRETRIES_WARNING}` | `15` | Tx Retry, Warning, %, по умолчанию (5/6 ГГц) |
| `{$TRIGGER_UPLINK_SPEED_PERIOD}` | `7d` | Скорость uplink сравнивается с максимумом за этот период |

</details>

## Нагрузка на контроллер

С интервалами по умолчанию каждая точка доступа даёт около **1.4 запроса в минуту**. Каждый сайт добавляет около 0.3 запроса в минуту, а основной хост — примерно по одному запросу на сайт раз в 30 минут.

| Точек доступа | Запросов в минуту (примерно) |
|---|---|
| 100 | ~150 |
| 500 | ~700 |

Чтобы снизить нагрузку, увеличьте `{$ITEM_STAT.JSON_UPDATE}` (радио, по умолчанию 2m) и `{$ITEM_CLIENTS.JSON_UPDATE}` (клиенты и аномалии, 5m).

## Ограничения

- **Только Zabbix 7.0** в этом релизе. Исходный шаблон для 7.4 указан в разделе [Благодарности](#благодарности).
- **Внутренний API.** Данные радио, uplink и аномалии берутся из недокументированного API UniFi. Он может измениться в будущих версиях.
- **Нет данных** о режиме канала Auto/Manual, режиме мощности и Rx Retry: API не отдаёт их надёжно.
- **Счётчики байт uplink** считаются с момента поднятия интерфейса и не совпадают с интерфейсом UniFi. Скорости (bps, pps) верные.
- **Самостоятельно установленный UniFi Network Application** без UniFi OS не проверялся. У него может не быть префикса `/proxy/network`.
- **Имена шаблонов и UUID** совпадают с исходным шаблоном `UniFi Network API`. Импорт обновит его, если он уже установлен.

## Устранение неполадок

| Симптом | Причина / решение |
|---|---|
| `URL rejected: Bad hostname` | `{$UNIFI_NETWORK_API_ADDRESS}` пуст, с опечаткой в имени, содержит пробелы или `https://`. Кнопка **Test** у элемента показывает подставленное значение макроса. |
| HTTP 401 | Неверный ключ или не прочитался секрет Vault. Смотрите `zabbix_server.log`, затем выполните `zabbix_server -R secrets_reload` (и `zabbix_proxy -R secrets_reload` на прокси). |
| Хосты сайтов есть, хостов точек нет | На основном хосте нажмите **Test** у *Access Points JSON (all sites)*, затем проверьте колонку **Info** у *Discovery Access Points*. |
| `devices request failed for N of M sites` | API не ответил по перечисленным сайтам. Discovery намеренно пропускает проход, чтобы точки не посчитались потерянными. |
| Группы не вложенные | Создайте или переименуйте родительскую группу ровно в `UniFi Network`. |
| На точке нет радио-элементов | Проверьте *Device Stat JSON*: макросы `{$SITE.REF}` и `{$AP.MAC}` заполняет discovery. Перезапустите *Discovery Access Points*. |

## Безопасность

- **Не вводите API-ключ в командной строке, в логах, чатах и заявках.** Используйте `read -s KEY` и `$KEY`. Если ключ утёк, удалите его в UniFi, создайте новый и обновите Vault.
- **Используйте для Zabbix отдельный API-ключ.**
- **Сырые ответы API не сохраняются** (история 0). Внутренний API устройств возвращает в том числе ключи устройства (`x_authkey` и другие). Шаблон вырезает их при предобработке, до записи в базу.
